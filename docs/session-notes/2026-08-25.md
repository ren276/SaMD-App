## Backend: 3 PRs merged, live ABHA enrolment reached

PR #18, #19, #20 — all merged today against `master`:

- **#18 `fix/abha-cert-base64-der-parse`.** ABDM sandbox's `GET /abha/api/v3/profile/public/certificate`
  returns `publicKey` as base64-encoded DER, not PEM text as the M1 tracker previously assumed
  (D6). Confirmed 2026-08-24 via a live probe against `abhasbx.abdm.gov.in`. Fix moved key parsing
  into `fetch_public_key_pem`, unified malformed-cert failures onto `SamdError(ABHA_UPSTREAM_ERROR)`
  / `NON_RETRYABLE` (previously `binascii.Error` was misrouted `RETRYABLE`, burning a real gateway
  session token on a call that could never succeed). Durable rule captured: *a mock that fabricates
  the wire shape is not a test of the wire shape* — `STUB_PUBLIC_KEY_B64_DER` is a hardcoded
  literal, not computed via `cryptography`, for exactly that reason.
- **#19 `fix/abha-send-otp-bearer-header`.** Live-verified: `enrollment/request/otp` 401s "Missing
  Credentials" (WSO2 900902) without `Authorization: Bearer <gateway session token>`, 400s "Invalid
  LoginId" with it. Falsified the earlier Phase A belief that enrollment/* endpoints carry no
  Authorization header. `send_otp` now requires `gateway_token`. `enrol_by_aadhaar` got the same
  header by extrapolation (same WSO2 gateway product/path prefix) — explicitly **not** live-verified
  at merge time.
- **#20 `fix/abha-get-profile-gateway-bearer`.** Extended the same gateway Bearer to `get_profile`
  (`profile/account`), also by extrapolation, not yet live-verified at merge time. Also pinned
  **Finding #6** (state-machine semantics): a `get_profile` failure after successful enrolment
  lands the transaction in `FAILED`, which a naive downstream reader could mistake for "ABHA
  creation failed." The discriminator already exists with no schema change —
  `state = 'FAILED' AND abha_number IS NOT NULL` means enrolment succeeded, only the profile read
  failed — pinned with a test, but deliberately no new state value/column/migration added. That's
  its own design ticket (see follow-ups below).

## Six durable findings from today

1. **Cert wire shape.** ABDM's `publicKey` is base64-DER, not PEM (PR #18, D6 correction).
2. **Gateway Bearer requirement.** `enrollment/request/otp` and (by extrapolation) `enrol_by_aadhaar`
   and `get_profile` all require the WSO2 gateway session token as `Authorization: Bearer`, not just
   the per-transaction `X-token` — contradicts the earlier Phase A belief (PR #19/#20).
3. **State-machine ambiguity (Finding #6).** `FAILED` after a successful enrolment is
   distinguishable from a failed enrolment only via `abha_number IS NOT NULL`, and nothing currently
   names that contract for downstream readers (PR #20).
4. **Local `.env` silently overrides "stub" test intent.** `backend/core/tests/` auto-loads
   `backend/core/.env` via pydantic-settings; a local `.env` set to `ABDM_MODE=live` makes
   stub-labeled tests silently hit the real ABDM sandbox (symptom: intermittent
   `RuntimeError: Event loop is closed` under real-network timing, easy to mistake for something
   else). Workaround in use: force `ABDM_MODE=stub` on the pytest invocation. Documented in
   `docs/abdm/M1-tracker.md`.
5. **Mobile number is masked-only on the wire.** `profile/account` never returns a full
   `mobile_number` — contract gap, documented (D4), not changed.
6. **ABHA live mobile is unmasked, contradicting old code comments.** The 2026-08-25 live
   `get_profile` observation returned 10 **unmasked** digits, contradicting two stale KDoc claims in
   the Android app (`isMaskedAbhaMobile`, `EnrolAbhaUseCase`) that said ABDM always masks it. Fixed
   in PR #21 — code was already correct either way, only the claim was wrong.
