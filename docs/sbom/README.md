# Software Bill of Materials (SBOM)

## Why this exists

Two regulatory gaps this closes (see `docs/regulatory-foundation.md`):

- **Off-the-shelf / third-party software validation** — IEC 62304 and ISO 14971 both require
  knowing exactly which third-party components (SOUP — Software Of Unknown Provenance) are in
  the shipped binary, at what version, so they can be risk-assessed and tracked for known
  vulnerabilities (e.g. Room, SQLCipher, Hilt, Compose, Coroutines).
- **Named security/compliance deliverable** — SBOM is a standard artifact expected in medical
  device cybersecurity submissions and security audits.

The SBOM is **generated from the resolved Gradle dependency graph**, not hand-maintained — it
reflects what actually ships, not what a spec file claims.

### Amendment, PROPOSED 2026-09-02, AWAITING OPERATOR SIGN-OFF

**The generated SBOM is necessary but no longer sufficient. A release SBOM is now the generated
file _plus_ the model companion.**

PR 4a is the first change to fall through the hole in the convention above. It adds three SOUP
components that a resolved Gradle dependency graph cannot see:

| Component | Why it is invisible to `cyclonedxBom` |
|---|---|
| Parakeet ASR model weights + `tokens.txt` | Files under `app/src/main/assets/`. Not a dependency at all. |
| sherpa-onnx runtime AAR | A file dependency (`implementation(files("libs/…"))`), because `com.k2fsa.sherpa.onnx` publishes nothing to Maven Central. |
| ONNX Runtime native libraries | Carried *inside* that AAR. Never a node in the graph. |

The most safety-relevant SOUP in the release is therefore the part the mechanism cannot record.
`docs/regulatory-foundation.md` §9 marks the SOUP/SBOM gap closed **conditional on the convention
being honoured**; this is the point where honouring it requires more than running the task.

**The companion:** `docs/sbom/model-soup-<YYYY-MM-DD>-v<versionName>.json`, CycloneDX 1.6,
hand-maintained, same naming and never-overwrite rules as the generated file. First one is
`model-soup-2026-09-02-v1.0.json`.

**What it must carry, per component:** exact version, SHA-256 of the bytes actually shipped
(per file for a multi-file model), licence of the shipped artifact — not of the upstream project,
which can differ — and, for a model, a model card recording training-corpus provenance and the
population it was *not* evaluated on.

**Two things worth copying into the next one:**

- **Pin the tokenizer separately from the weights.** A mismatched vocabulary produces fluent,
  plausible, wrong text rather than an error. It is the smallest file in the model and the only
  one whose corruption is silent.
- **Read versions off the artifact, never off documentation.** The bundled ONNX Runtime is
  1.27.1, read out of the consumed `.so`. The sherpa-onnx Android docs say 1.17.1. Pinning the
  documented value would have recorded a component that does not ship.

**Checked on-device, not just asserted — but not by CI.** `SherpaOnnxTranscriptionServiceTest`
hashes each shipped model asset and compares it against the pinned value, so the companion cannot
silently drift from the APK it actually shipped in. It runs on an emulator or device (`arm64-v8a`
or `x86_64`), not in CI: the storage amendment below means the weights the test hashes are not in
the repository CI checks out, so CI has nothing to hash. Do not describe this as a CI gate until
that changes.

**Amendment, PROPOSED 2026-09-02, AWAITING OPERATOR SIGN-OFF — storage decision.** The Parakeet
weights themselves are stored LOCAL-ONLY (gitignored), not committed: the encoder alone is 622 MiB,
over GitHub's 100 MiB per-file limit, and git-LFS was evaluated and declined (its free tier would
not survive a second model version). The per-file SHA-256 manifest in the model companion is
therefore the single source of truth for which bytes shipped, not the git history.

**Known limitation, not a defect:** because the weights are not in the repository, CI cannot build
or run anything that exercises the flag-on ASR path — that egress proof runs on-device (Pixel
emulator-5554) in PR 4b, not in CI.

## Format

[CycloneDX](https://cyclonedx.org/) JSON, schema 1.6, generated by the
`org.cyclonedx.bom` Gradle plugin (`app/build.gradle.kts`). Scope is the `:app` module's
`devReleaseRuntimeClasspath` — the `dev`-flavor release dependency set, one of three
(`dev`/`staging`/`prod` × `environment`); `cyclonedxBom` is currently wired to `dev` only. See
PR 4b-1's `PROGRESS.md` entry for why the plain, pre-flavor-split `releaseRuntimeClasspath` name
silently stopped resolving.

## Regenerating

```
./gradlew :app:cyclonedxBom
```

This writes `docs/sbom/sbom-latest.json`. **Rename it** before committing, using the release
date and app `versionName` from `app/build.gradle.kts`:

```
mv docs/sbom/sbom-latest.json docs/sbom/sbom-<YYYY-MM-DD>-v<versionName>.json
```

## Convention

**A new SBOM is generated and committed at every tagged release**, not just once. Never
overwrite a previously committed SBOM — each one is a point-in-time record tied to a shipped
version, and prior releases still in the field need their own record. `sbom-latest.json` itself
is a build artifact and should not be committed (only the renamed, dated file).
