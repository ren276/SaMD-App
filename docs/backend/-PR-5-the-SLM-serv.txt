## 0. What was built

A new FastAPI service at `slm_service/`, built beside `litert_edge_engine/edge_server.py`
and sharing no code with it. The demo server was read for transport shape only and is
unmodified. MEASURED: `git status` shows no change under `litert_edge_engine/`.

| File | What it holds |
|---|---|
| `slm_service/__init__.py` | `GENERATE_PATH` and `HEALTH_PATH` as named constants |
| `slm_service/config.py` | environment-derived settings, validated eagerly |
| `slm_service/errors.py` | the `SAMD-SLM-8xxx` registry and the RFC 9457 envelope |
| `slm_service/schemas.py` | request and response shapes, `extra="forbid"` |
| `slm_service/identity.py` | `model_id` and the artifact digest, derived from the artifact |
| `slm_service/engine.py` | load, greedy generation, derived `finish_reason`, deadline, cancel |
| `slm_service/admission.py` | the in-process bounded queue |
| `slm_service/security.py` | `X-SLM-Service-Token`, as pure ASGI middleware |
| `slm_service/observability.py` | the per-request log and its field allowlist |
| `slm_service/app.py` | the application, the lifespan, the two routes |
| `slm_service/__main__.py` | entry point, single worker |
| `deploy/slm/Dockerfile` | CUDA base image |
| `deploy/slm/docker-compose.yml` | explicit GPU reservation, loopback-only publish |
| `tests/slm_service/` | 96 tests |

Surface: `POST /v1/generate` and `GET /health`. Nothing else. There is no
`/v1/chat/completions`, no `/v1/models`, no `/docs`, no `/openapi.json`
(`docs_url`, `redoc_url` and `openapi_url` are all `None`).

### Properties, and where each one lives

- **Load in a lifespan.** `slm_service/app.py`, the `lifespan` context manager. Nothing
  loads at module import and nothing loads per request. A load failure re-raises, so
  the process exits with a log line rather than serving.
- **Derived identity.** `slm_service/identity.py`. `model_id` and `model_sha256` are read
  off the artifact on disk. There is no configuration value and no literal that can
  supply either, and an underivable value raises rather than defaulting. MEASURED: the
  service reports `model_sha256` `2db5482b20d746879bb3ef79b5203e9075a2e2b98f54ec7c2f281c1477ddc550`,
  which equals both the Hugging Face content-addressed blob name written by the
  downloader and the output of coreutils `sha256sum` on `model.safetensors`.
- **Honest `finish_reason`.** `Engine._derive_finish_reason`. Read off the generation in
  this order: a caller-declared stop sequence fired, the last token is in the artifact's
  EOS set, the completion reached the served ceiling, otherwise `error`. Nothing in the
  service can emit a literal `"stop"`.
- **Input bound in tokens, rejected.** Enforced twice: in the handler before a GPU slot is
  taken, and again at the engine boundary. Both are real and both are tested. Tokenization
  passes `truncation=False` explicitly. The `413` names the measured length and the limit
  and carries no part of the prompt.
- **Greedy decoding.** A fresh `GenerationConfig(do_sample=False, num_beams=1, ...)` is
  passed to `generate`, so the artifact's own generation config (which carries
  `do_sample: true`, `temperature: 1.0`, `top_k: 64`, `top_p: 0.95`, MEASURED from
  `generation_config.json`) does not supply defaults. The seed is applied and echoed.
  MEASURED: ten generations of the same prompt produced byte-identical text.
- **One worker, a bounded queue.** `slm_service/admission.py`. One generation runs, a
  configured number wait, anything beyond gets `503` / `SAMD-SLM-8005` with `Retry-After`
  immediately.
- **A wall clock the service owns.** A stopping criterion checked at every token boundary,
  default 40 s, strictly inside the caller's 50 s read budget. On expiry the service drops
  the tensors, calls `torch.cuda.empty_cache()` and returns `504` / `SAMD-SLM-8007`.
- **Disconnect actually stops generation.** The handler runs `generate` on a worker thread
  and polls `request.is_disconnected()` on the event loop; a disconnect sets an event that
  a stopping criterion reads at the next token boundary.
- **Auth.** `X-SLM-Service-Token` against setting `SLM_SERVICE_TOKEN`, compared with
  `hmac.compare_digest`. Fails closed when the setting is unset or blank, and when the
  header is absent or wrong. The value is never read into a response, a log or a repr.
  Startup also refuses when the setting is unset.
- **Health.** Every field is read from live state or the loaded artifact at request time.
  There is no static literal anywhere in the handler.
- **Per-request log.** One JSON line, built from an explicit field allowlist. The prompt
  and the generated text are not parameters of the logging function, so the prohibition is
  structural rather than a habit of the call sites.

## 1. Measured latency

Ten sequential generations, service freshly started, representative readback prompt
(268 prompt tokens: a five-field snapshot, a four-line prescription set and a follow-up
line, wrapped in the artifact's chat template). `max_tokens` 512. Wall clock measured at
the HTTP client, so it includes request, tokenization, generation, decode and response.

| Run | Wall clock | `finish_reason` | prompt tok | completion tok | tok/s |
|---:|---:|---|---:|---:|---:|
| 1 (cold) | 4673.4 ms | stop | 268 | 207 | 44.29 |
| 2 | 4327.6 ms | stop | 268 | 207 | 47.83 |
| 3 | 4352.8 ms | stop | 268 | 207 | 47.56 |
| 4 | 4354.3 ms | stop | 268 | 207 | 47.54 |
| 5 | 4387.7 ms | stop | 268 | 207 | 47.18 |
| 6 | 4352.8 ms | stop | 268 | 207 | 47.56 |
| 7 | 4358.9 ms | stop | 268 | 207 | 47.49 |
| 8 | 4357.1 ms | stop | 268 | 207 | 47.51 |
| 9 | 4354.8 ms | stop | 268 | 207 | 47.53 |
| 10 | 4382.8 ms | stop | 268 | 207 | 47.23 |

| Figure | MEASURED |
|---|---|
| p50, all ten runs | **4356.0 ms** |
| p95, all ten runs | **4544.9 ms** |
| First call | 4673.4 ms |
| Steady state (runs 2 to 10), p50 | 4354.8 ms |
| Steady state, p95 | 4385.7 ms |
| Cold-start penalty on the first call | **318.6 ms** |
| Sustained decode rate, steady state p50 | **47.53 tokens/s** |
| Completion length, full readback | 207 tokens, identical on all ten runs |

A second run of the same ten, taken on an already-warm process, gave p50 4398.0 ms and
p95 4570.3 ms. The two runs agree to within about 1 percent.

**Startup:** 14.0 s wall from process start to `Application startup complete`, with the
artifact warm in the page cache. That includes the digest computation, which is the larger
half: `sha256` over the 9.543 GiB weight file took **28.56 s** on a cold page cache and
6.6 s warm, MEASURED. The digest is recomputed on every start and is not cached, because a
cache keyed on size and mtime is exactly the check that reports satisfied while the thing
it checks has changed underneath it.

### Does a full readback fit inside the 40 s service cap?

**MEASURED: yes, with a margin of roughly 9x.**

| Scenario | prompt tok | completion tok | wall clock |
|---|---:|---:|---:|
| Four-drug record (representative) | 268 | 207 | 4391 ms |
| Ten-drug record (stress) | 428 | 328 | 7008 ms |
| Generation driven to the 512-token ceiling | 286 | 512 | **10819 ms** |

The worst case the current ceiling permits is 10.8 s, which is 27 percent of the 40 s cap.

The contract's §4.3 arithmetic said the service must sustain at least 12.8 tokens/s for a
512-token generation to fit in 40 s, and recorded that no measurement existed. **MEASURED:
47.53 tokens/s, about 3.7x the requirement.** The contract's INFERRED "very likely
comfortable on GPU" is confirmed on this hardware.

### `max_tokens` recommendation

**Keep 512. Do not reduce it, and do not widen the 40 s cap.**

The reasoning is the contract's own: `max_tokens` should be sized so that truncation is
rare, not merely detectable. MEASURED, a representative four-drug readback completes in
207 tokens and an unusually large ten-drug readback completes in 328. 512 leaves about 1.6x
headroom over the stress case, and the cost of that headroom is bounded at 10.8 s, well
inside the cap. Lowering to 384 would still cover the stress case but would put the backstop
within 17 percent of an observed real completion, which is where a backstop starts firing
routinely. Raising it is unnecessary and would spend cap margin for nothing.

INFERRED, not measured: a record with more than about fifteen prescription lines could
exceed 512 completion tokens. If `finish_reason: length` is ever seen in production on a
real record, the lever is prompt brevity first and `max_tokens` second, and there is cap
headroom for 768 (about 16 s) if it is genuinely needed.

## 2. Resident VRAM

MEASURED with the model loaded and idle, from the service's own `/health` (which reads
`torch.cuda.memory_allocated` and `memory_reserved`) and from `nvidia-smi`:

| Figure | Bytes | GiB |
|---|---:|---:|
| Torch allocated | 10,255,397,376 | **9.551** |
| Torch reserved | 10,387,193,856 | 9.674 |
| GPU total | 16,708,927,488 | 15.561 |
| Whole-GPU used with the service up (`nvidia-smi`) | | 10.35 (10597 MiB) |
| Whole-GPU used with the service down | | 0.41 (423 MiB, desktop compositor) |

So the service's own footprint measured at the driver is about **9.94 GiB**, and the weight
file on disk is 10,246,621,918 bytes (9.543 GiB). The KV cache for a 268-token prompt and a
512-token completion is small enough to sit inside the allocator's existing reservation:
allocated rose by only 8.5 MB between a freshly loaded service and one that had served ten
generations.

**This is the figure that feeds the open question about the target phone, which nobody has
sized.** Stating it plainly: 9.55 GiB of bfloat16 weights is not a phone-resident model.
INFERRED, and worth someone checking properly rather than taking from here: reaching a
typical 8 GiB or 12 GiB handset would need INT4 weight quantization (roughly 2.4 GiB for
this parameter count) plus dropping the vision and audio towers, and no such artifact
exists in this repository. `models/litert_bundle/` contains one 782-byte JSON manifest and
no weights, as the 2026-09-09 audit recorded, and that is still true.

## 3. Contract corrections, for the main machine

The contract at `docs/backend/slm-service-contract.md` was written before this service
existed. Holes in it are expected. Each item below is either already fixed in this repo's
copy, or is a finding the canonical copy needs.

### 3.1 The endpoint path. **Fixed here. The canonical copy needs the same edit.**

MEASURED: in the 459-line original, no generation endpoint path appears anywhere. `grep`
for `POST`, `/v1/`, `/api/` and `generate` returns only `/v1/chat/completions` (in the
sentence disowning the sample app) and `/health`. Both sides had to build against a path
neither could look up.

The edit, inserted directly under the `## 2. Request` heading and above `### 2.1 Shape`:

```
**Endpoint: `POST /v1/generate`.**

Named here because v1 of this document specified the request, the envelope, the error vocabulary
and the timeout budget without ever naming the path they travel on, while both sides had to build
against one. PR-4 chose `/v1/generate` and pinned it as a named constant on the calling side, so
this line makes the document match what was built rather than leaving the single field neither side
could look up. The other path this service exposes is `GET /health` (§5.1).
```

`/v1/generate` is pinned in this service at `slm_service/__init__.py` as `GENERATE_PATH`,
matching what PR-4 pinned on the calling side. **Apply the same paragraph to the canonical
copy so the two do not drift.**

### 3.2 §3.1's example `model_sha256` is the digest of the wrong file

MEASURED. The example envelope gives
`"model_sha256": "cc8d3a0ce36466ccc1278bf987df5f71db1719b9ca6b4118264f45cb627bfe0f"`.
In the cached snapshot of `google/gemma-4-E2B-it`, that is the content-addressed blob name
of **`tokenizer.json`**. The weight file's digest is
`2db5482b20d746879bb3ef79b5203e9075a2e2b98f54ec7c2f281c1477ddc550`.

The rule in §3.2 is right and the example under it points at the tokenizer. An implementer
who anchors on the example hashes the wrong artifact and gets a digest that is stable across
a weight change, which is precisely the failure §3.2 exists to prevent. **Replace the example
value, or mark it explicitly as illustrative and not from this artifact.**

### 3.3 §3.2 requires deriving `model_id`, and the artifact does not carry its own name

MEASURED, two separate problems.

First, `config.json` for `google/gemma-4-E2B-it` has **no `_name_or_path` key** (top-level
keys are `architectures`, `audio_config`, `audio_token_id`, `boa_token_id`, `boi_token_id`,
`dtype`, `eoa_token_id`, `eoa_token_index`, `eoi_token_id`, `eos_token_id`, `image_token_id`,
`initializer_range`, `model_type`, `text_config`, `tie_word_embeddings`,
`transformers_version`, `video_token_id`, `vision_config`, `vision_soft_tokens_per_image`).
There is nothing inside the artifact's files that states the repository it is served as. This
service derives it from the Hugging Face cache directory layout
(`models--google--gemma-4-E2B-it`), which is written by the downloader from the repo id
actually fetched. That is a derivation from the artifact on disk, but it is weaker than §3.2
implies, and it stops working for an artifact deployed as a plain directory.

Second, and worse: where `_name_or_path` **is** present it can name an upstream ancestor
rather than the served repository. MEASURED on the second real artifact in the local cache,
`sentence-transformers/all-MiniLM-L6-v2`, whose `config.json` reports
`nreimers/MiniLM-L6-H384-uncased`. Preferring that field would make a correctly deployed
service report a name the caller's pin does not match, and would make two different
fine-tunes of one ancestor report the same `model_id`.

**The contract should state which source is authoritative**, and in what order. This service
uses cache layout first, `_name_or_path` second, and refuses to start when neither answers.

### 3.4 There is no error code and no outcome row for an authentication failure

§4.4 requires the backend-to-service hop to be authenticated and leaves the mechanism to the
service. But §4.1's registry has no code for a rejected credential, and §4.2's table, which
asserts totality in prose and forbids an "other" row, has **no row for a 401**.

This service allocates **`SAMD-SLM-8008` / 401 / "Service authentication failed"** from the
same previously unused 8xxx block. The canonical registry must either adopt that number or
choose another before anything ships, since §9.1 discipline makes it permanent once a caller
branches on it.

§4.2 also needs a row. `PAYLOAD_REJECTED` is the wrong target: the payload was never
examined, and a caller that retries a rejected credential the way it retries a bad field will
loop. §4.2's own rule says the correct response to a failure with no row is to add a row, not
to widen an existing bucket, so this reads as a new `SlmCallOutcome` value alongside the
`QUEUE_FULL` gap §4.2.1 already records.

### 3.5 §2.2 does not say whether `prompt` arrives already wrapped in chat control tokens

This is the most consequential hole found, and a test caught it rather than reasoning.

§2.2 says the service performs no chat-template application, no role wrapping and no
system-prompt injection, and that the prompt "is assembled by the device's seam from a
versioned template and arrives complete". It does not say what "complete" includes.

MEASURED on this artifact's tokenizer: **`add_special_tokens` is a no-op.** The record text
and the record text with `add_special_tokens=True` both tokenize to 259 tokens, first token
`3048`, with no BOS. The BOS token appears only because the artifact's own chat template
writes the literal string `<bos>`. So anything the template does not write is simply absent,
and the service cannot add it without becoming the thing §2.2 forbids.

The consequence, MEASURED end to end on the running service, same record, same settings:

| Prompt form | `finish_reason` | completion | text |
|---|---|---:|---|
| Record sent raw | `length` | 512 tok | `"\n\nPatient.\n\nPatient.\n\nPatient."` repeated to the ceiling |
| Record wrapped by the artifact's chat template | `stop` | 207 tok | a correct plain-language readback |

A degenerate completion of that kind is not an error at any layer. It arrives over a `200`,
it passes the stream sanitizer untouched, and **it passes the output grounding gate by
construction** for the same reason a truncated readback does: it introduces no drug name and
no dosing numeral the record did not already contain. It contains almost nothing at all.

In this instance truncation caught it, because the degenerate loop ran to the ceiling and
reported `length`. That was luck. A degenerate completion that emits EOS early would report
`stop` and be indistinguishable from a correct readback in every field of the envelope.

**The contract should state that `prompt_template_version` `slm-readback-v1` emits the fully
templated string, including the artifact's leading BOS and its turn control tokens, and that
the service feeds it verbatim.** Until it does, the one property this contract exists to
provide is not provided: the caller cannot tell whether what came back is a readback.

This service cannot reject on the condition, because the contract does not authorise a
rejection, so it makes it visible instead: the per-request service log carries
`prompt_starts_with_bos`, derived from the first token id of the tokenized prompt.

### 3.6 §5.1's "load state" cannot discriminate under §5.2's lifespan load

§5.1 says load state "distinguishes starting from serving". §5.2 requires the model to load in
a lifespan hook. Those two do not compose: a uvicorn worker does not accept connections until
lifespan startup has returned, so an external caller can never observe `loading`. MEASURED:
during the 14 s startup, `GET /health` is refused at the TCP layer, not answered with
`loading`.

The field is implemented honestly (it is read from live state, never a literal) but it can
only ever read `loaded` from outside. Either accept that and say so, or specify background
loading, which would make the state observable at the cost of a window where the service is
up and cannot serve.

### 3.7 `SAMD-SLM-8004` is unreachable under fail-fast startup, and is flagged rather than dressed up

Same root cause as 3.6. Because a load failure is a startup failure, there is no live path on
which a request meets an unloaded model. The guard exists in `slm_service/app.py` and is
correct, but **it is a defensive guard, not a live path**, and no test asserts it fires in
production conditions, because none honestly can.

Saying so explicitly, because a guard that can never fire while a test reports it satisfied is
the eighth instance's exact shape, and it would be easy to write a test here that manipulates
`app.state` into an impossible configuration and then claim the path is covered.

### 3.8 `api-contract.md` §0.5 and §0.6 are not on this machine

The contract's Conventions section says §0 of `api-contract.md` applies unchanged, including
the success envelope (§0.5) and the RFC 9457 error envelope (§0.6). MEASURED: the only copy of
`api-contract.md` on this machine is inside the stale read-only clone, which this change is
forbidden to read line numbers from and did not use.

The error envelope here is therefore **INFERRED** from RFC 9457 itself plus this contract's
own §4.1: `type`, `title`, `status`, `code`, `detail`, `instance`, and `errors[]` on a
`SAMD-SLM-8001`, served as `application/problem+json`. **Someone with the canonical
`api-contract.md` must reconcile the field names.** If §0.6 spells the code field differently,
this service's responses are wrong in a way no test here can detect.

### 3.9 The pinned `transformers` floor in the repo cannot load this artifact

Not a contract item, but it blocks anyone reproducing this. MEASURED: the repository's
`requirements-docker.txt` pins `transformers>=4.40.0`, and the interpreter on this machine has
4.44.2 installed, which raises
`ValueError: The checkpoint you are trying to load has model type gemma4 but Transformers does
not recognize this architecture.` The artifact's `generation_config.json` records
`transformers_version: 5.5.0.dev0`.

This service is built and measured against **`transformers==5.5.0`**, pinned exactly in
`deploy/slm/requirements.txt`, installed into a dedicated virtualenv at
`/media/acps/twoTBDrive/venv-slm` rather than into the machine's base environment, which was
left untouched.

## 4. Deployment, and what was not verified

`deploy/slm/Dockerfile` uses `pytorch/pytorch:2.4.1-cuda12.4-cudnn9-runtime`, a CUDA base
image, and does not reinstall torch from PyPI. `deploy/slm/docker-compose.yml` declares an
explicit `deploy.resources.reservations.devices` GPU reservation, pins `SLM_DEVICE=cuda`,
publishes only to `127.0.0.1`, and attaches the service to a private bridge network that
backend/core joins. `SLM_SERVICE_TOKEN` is required from the operator's environment and is
absent from the file.

**The image was not built and the container was not run.** MEASURED and stated plainly rather
than glossed: Docker's root directory is `/var/lib/docker` on a filesystem with **5.5 GiB
free at 100 percent used**, and the CUDA base image alone exceeds that. `docker compose config`
parses the file and resolves the GPU reservation and the `127.0.0.1` host binding correctly,
which is syntax and topology confirmation only.

**Everything measured in sections 1, 2, 5 and 6 was measured against the service running
directly under uvicorn on this host, not in the container.** INFERRED: containerised latency
should be within noise of these figures, since the GPU, the driver and the artifact are the
same and the container adds no proxy hop. Not measured. Someone with disk space should run
the suite against the built image before this ships.

Two design choices worth naming, both aimed at the shape this project keeps hitting:

**No fake engine anywhere.** Every service test runs against a real uvicorn process with the
real 9.55 GiB artifact resident on the real GPU. A test asserting against a stand-in that
re-implemented this service's own policy would keep reporting satisfied while the artifact
changed underneath it.

**The digest witnesses are not this service's code.** `test_identity.py` checks the derived
digest against the Hugging Face content-addressed blob name, written by a different program at
download time, and against coreutils `sha256sum`, a different implementation of the same hash.
A test that recomputed the digest with the same `hashlib` call the service uses would agree
with the service no matter what either of them did.

Only one service process is alive at a time, enforced by the fixture. Two are not slower, they
are an out-of-memory: 2 x 9.55 GiB does not fit in 15.561 GiB.

## 6. Mutation checks

The standing rule from eight instances in this project is that a check reporting
satisfied while the thing it checks has changed underneath it is the characteristic bug
here. So every property this service establishes was broken deliberately.

Procedure, for each row: hash the file, apply a replacement whose needle is asserted
**unique against the whole file** (not against a neighbourhood), run the named tests and
require RED, restore from a byte-for-byte copy, confirm the hash is unchanged, then run
the same tests again and require GREEN. A hang counts as RED but is not allowed to stall
the harness, so every run carries a 150 s per-test timeout and a 900 s process timeout.

**20 mutations. All 20 went RED, restored byte-identical, and came back GREEN.**

| # | Mutation | Property it removes | Test that caught it | RED | Restored identical | GREEN |
|---|---|---|---|---|---|---|
| M01 | `_derive_finish_reason` returns the literal `"stop"` | honest finish reason, the sample service's exact defect | `test_a_truncated_readback_is_distinguishable_from_a_complete_one` | yes | yes | yes |
| M02 | tokenizer set to `truncation=True`, handler bound disabled | over-length prompt rejected, never truncated | `test_overlong_prompt_is_rejected_and_not_truncated` | yes | yes | yes |
| M03 | digest replaced with a hardcoded hex string | digest derived from the artifact | `test_digest_changes_when_one_byte_changes` | yes | yes | yes |
| M04 | `_derive_model_id` returns a literal repo id | model_id derived from the artifact | `test_cache_layout_wins_over_an_upstream_name_in_config` | yes | yes | yes |

## 7. What a test caught that reasoning did not

Three things. All three were found by running the thing, not by reading it.

**1. The prompt must arrive already wrapped in the artifact's chat control tokens, and
nothing in the contract says so.** Covered in full at §3.5 above. The first end-to-end
generation returned `"\n\nPatient.\n\nPatient.\n\nPatient."` repeated to the token ceiling.
Reasoning had accepted §2.2's "arrives complete" as settled and moved on. This is the most
serious finding in the change: a degenerate readback that ends in EOS rather than at the
ceiling would report `finish_reason: stop` and pass every field of the envelope, the stream
sanitizer, and the output grounding gate.

**2. Deriving `model_id` from `config.json` `_name_or_path` is wrong, and the second real
artifact proved it.** The first version of `identity.py` preferred `_name_or_path` and fell
back to the cache layout. `test_swapped_artifact_changes_model_id_and_digest` failed with
`assert 'nreimers/MiniLM-L6-H384-uncased' == 'sentence-transformers/all-MiniLM-L6-v2'`.
That field records what a checkpoint was initialised from, not what it is served as. The
served artifact here has no `_name_or_path` at all, so this would never have shown up
against `google/gemma-4-E2B-it` alone, and it would have shipped as a latent defect that
fires the first time someone deploys a fine-tune whose config names its base. The precedence
is now cache layout first, and two tests pin it.

**3. The auth middleware silently disabled disconnect detection.** Writing auth as
`@app.middleware("http")` was the obvious choice and every auth test passed. The disconnect
test failed, showing a generation that ran to completion, `finish_reason: stop`, 207 tokens,
after the caller had already gone. Reasoning had treated auth placement and disconnect
detection as unrelated concerns. They are coupled through the ASGI `receive` callable. This
one is close in shape to the eighth instance from PR-4: a correct-looking guard made
unreachable by where a middleware sits. Preserved as M16 so it stays caught.

One smaller thing, caught by the harness rather than by a test: the first mutation table had
a needle that matched twice (M07 above). The uniqueness assertion is worth keeping in any
future mutation run in this project.

### 14.6 Property 7: the service does not wrap, and the brief's premise needs correcting

Two corrections, both MEASURED.

**First, the service performs no control-token wrapping at all, by design.** There is no
`apply_chat_template` and no `chat_template` reference anywhere under `slm_service/`
(grep returns nothing). `Engine.generate` calls the tokenizer on `body.prompt` directly.
`Engine.prompt_starts_with_bos` says so in terms: `"The service applies no chat template and
injects no preamble, so the prompt must arrive complete"` (verbatim quote from
`slm_service/engine.py`, flagged). So property 7 as the brief words it, "prove the service
wraps the prompt in the artifact's chat control tokens", **cannot be proved, because the
service does not do it.** Wrapping is the caller's obligation. This is section 3.5's finding,
unchanged, and the container does not alter it.

**Second, the brief's description of the raw-path failure is inverted.** The brief states
that an unwrapped prompt "ends at EOS, and reports `finish_reason stop`, so it passes the
device sanitizer and grounding gate by construction". MEASURED in the container, on the same
record, it does not: it runs to the ceiling and reports `length`.

| Prompt form | HTTP | `finish_reason` | completion | text |
|---|---:|---|---:|---|
| Record sent raw, 259 tok | 200 | `length` | 512 | `"\n\nPatient.\n\nPatient.\n\nPatient."` to the ceiling |
| Record wrapped by the artifact's template, 268 tok | 200 | `stop` | 207 | a correct plain-language readback |

This reproduces section 3.5's table exactly. The distinction matters because it is the whole
of the residual risk: in *this* instance truncation caught the degenerate loop and reported
`length`, which a caller can see. Section 3.5's point, which stands, is that this was luck. A
degenerate completion that happened to emit EOS early would report `stop` and be
indistinguishable from a correct readback in every field of the envelope. The brief has
folded the hypothetical danger into the measured observation; the measured observation is
the milder of the two.

What *can* be proved, and is, is the positive half: the service feeds the prompt verbatim, so
a correctly wrapped prompt produces a correct readback where the raw path degenerates. The
wrapped prompt's tokenisation begins `<bos><|turn>user\n` and ends `<turn|>\n<|turn>model\n`
(268 tokens against the raw record's 259), and it yields the correct 207-token readback shown
above, ten times out of ten, byte-identical.

The service's one defence is observational, and it works. MEASURED across this session's
requests, the per-request log carries `prompt_starts_with_bos`: `true` on 13 wrapped
requests, `false` on 5 raw ones. An operator can see the condition. A caller cannot.

Section 3.5's recommendation is unchanged and is now the single most important open item
from this session: **the contract must state that `prompt_template_version slm-readback-v1`
denotes the fully templated string, including the artifact's leading BOS and its turn control
tokens, and that the service feeds it verbatim.**

## 15. PR-5b, 2026-09-21: templating into the service, an injection guard, the deadline fix, and the mount

Section 14 proved the container ran correctly. It also recorded why, end to end, it would
have produced nothing usable: the service applied no chat template, the device sends plain
text, and PR-4's proxy forwards it unchanged, so every readback would have degenerated to
`"Patient."` repeated and been refused downstream as `OUTPUT_TRUNCATED`. PR-5b closes that,
and three things next to it.

### 15.1 Templating moves into the service

`Engine.apply_template` applies the loaded artifact's own
`tokenizer.apply_chat_template([{"role": "user", "content": prompt}], tokenize=False,
add_generation_prompt=True)`. Derived from the artifact, never a written grammar: a literal
`"<bos><|turn>user\n"` would survive a change of artifact and tokenize into ordinary text,
which degenerates rather than erroring, and degeneration is precisely what this change
exists to remove.

**Decision, stated because the brief asks for it: the whole caller string goes in as one
user turn, and is not split into a system turn and a user turn.** MEASURED, this artifact's
template does support a system turn: `apply_chat_template` with a system message renders
`<bos><|turn>system\nSYS<turn|>\n<|turn>user\nHELLO<turn|>\n<|turn>model\n`, so the
capability is there and the choice is not forced by the artifact.

It is refused anyway, on three grounds:

1. Splitting means deciding where the instruction ends and the record begins. The caller
   sends one string whose shape is owned by `prompt_template_version`, and the only way for
   the service to find that boundary is to parse clinical text. A service that parses the
   record to decide what to put in a system turn is doing clinical reasoning about a record
   a physician has already approved.
2. The contract's unit is `prompt_template_version`. If the service split the string, the
   version would no longer describe what reached the model, and the field that exists to
   make the prompt reproducible would stop doing so.
3. It would change the contract shape silently, which the brief forbids and which nothing
   here needs. MEASURED, one user turn produces a correct readback: `finish_reason stop`,
   207 completion tokens, byte-identical across ten runs.

If a system turn is ever wanted, it belongs in the device's template and in a new
`prompt_template_version`, not in a service-side split of a string the service did not
compose.

The input bound now measures the templated string, because that is what occupies the model's
context. MEASURED on this artifact the template adds a fixed 9 tokens (259 plain, 268
templated), so a caller sitting exactly on 2048 is refused at 2057. That is the safe
direction, and the 413 detail says which number was measured.

`prompt_starts_with_bos` is kept and its meaning has inverted. It no longer reports what the
caller sent; it reports whether the service's own templating produced what it should, and is
true under correct operation. It is still derived from the first token id rather than
asserted, because it is the only place a template that stopped writing BOS would be visible:
that failure does not raise.

### 15.2 The injection guard, SAMD-SLM-8009

Before templating, a prompt containing any of the loaded artifact's special or added tokens
as text is refused with the new code `SAMD-SLM-8009`, HTTP 422.

The set is derived, never written: the union of `tokenizer.all_special_tokens` and
`tokenizer.get_added_vocab()`. MEASURED on this artifact the two agree at 24 entries,
including `<bos>`, `<|turn>`, `<turn|>`, `<|channel>`, `<channel|>`, the tool and image and
audio tokens. A hardcoded list would keep reporting a clean prompt after the artifact renamed
its tokens, which is the same defect as a hardcoded `model_id`. The engine refuses to finish
loading if the set comes back empty, because an empty set is a guard that admits everything
while still reporting that it ran.

Matching is substring matching on the caller's raw string, deliberately, rather than asking
the tokenizer what it would produce. Asking the tokenizer whether it would emit a control
token is asking the thing being attacked to grade the attack.

**Refused, never stripped.** The caller text carries a physician's free-text working
diagnosis and a health worker's free-text question. Silently editing that on its way to a
readback the clinician has already approved is worse than refusing to serve it, and the
detail says `rejected, not sanitised` so that a caller reading it cannot conclude its text
was cleaned up and sent. The detail names the tokens found, which are fixed vocabulary
strings and carry no PHI, and never any part of the prompt.

The guard runs before the length bound, so it inspects exactly what the caller sent, before
anything has been added to it. MEASURED: an over-length prompt that also carries control
tokens is refused as an injection (422), not as a length violation (413).

It also closes double-templating. A caller that assembled the prompt the way PR-5 required is
now refused rather than templated twice. This matters because double templating does not
error on its own: it tokenizes, generates and returns a 200, so without the guard the
transition from PR-5 to PR-5b would silently change what the model sees.

The per-request log carries `control_tokens_found`, a count. MEASURED, the count and nothing
else: the log line for an injected prompt containing `PT-4471-K` and `Metformin` contains
neither string.

### 15.3 The deadline is armed at arrival

Section 14.4 recorded that `generation_deadline_s` bounded decode only, because `started` was
set after `await admission.acquire()` and the deadline criterion was armed inside
`Engine.generate`. A queued request was therefore granted a fresh full budget when it reached
the model.

The clock is now read at the top of the handler and the generation is given what is left of
it. If nothing is left, the request is abandoned before generation starts, with
`SAMD-SLM-8007` and the log outcome `deadline_expired_in_queue`.

MEASURED, at a 3 s deadline with two concurrent requests, which is the shape that isolates
this:

| Deadline armed | First request | Second request |
|---|---:|---:|
| After admission (before PR-5b) | 504 at 3.07 s | 504 at **6.09 s** |
| At arrival (PR-5b) | 504 at 3.06 s | 504 at **3.06 s** |

**A correction to the brief's framing, MEASURED.** The brief describes the exposure as a
queued 512-token request answering near 73 s. That figure came from section 14, where a
512-token request meant a degenerate generation running to the ceiling in about 11 s. Once
templating lands, the same request is a correct readback that ends at EOS after 207 tokens in
about 4.4 s, so the realistic worst case at the shipped settings is smaller than 73 s. The
defect was real and is fixed; its magnitude at the shipped settings is INFERRED to be roughly
4.4 s of wait per queued request plus a fresh 40 s, not 73 s. This mattered in practice: it
made the first version of the regression test pass against the bug, because the test assumed
generations that no longer happen.

Alongside it, a request whose expected wait alone would exceed its remaining budget is
refused at arrival with 503 and `Retry-After`, rather than admitted to expire in the queue. A
request refused now can be retried; one that expires in the queue has held a slot, produced
nothing, and told the caller only that it timed out. MEASURED with the control removed, four
concurrent requests against a 6 s deadline produced `[200, 504, 504, 504]`; with it, at least
one fast 503.

The estimate comes from `WaitEstimator`, the worst of the last eight completed generations on
this artifact and this GPU, multiplied by the number of admitted requests ahead. The worst
rather than the mean, because admitting onto a queue of slow generations because the average
is fast is the expensive direction. Cancelled generations are not observed, since their
duration measures the client rather than the service.

**A stated gap.** Before the first generation completes there is no sample, the estimate is
`None`, and no arrival-time refusal can fire. On a freshly started service the deadline is
the only protection until one generation has finished. Inventing a default would mean
refusing real traffic on a number nobody measured, which this project does not do.

The arrival-time refusal reuses `SAMD-SLM-8005` rather than taking a tenth code. The caller's
correct action is identical in both cases, honour `Retry-After` and come back, so a second
code would widen the contract surface for a distinction the caller cannot act on. The service
log carries the distinction, `queue_wait_exceeds_deadline` against `queue_full`, for whoever
is tuning the queue.

> remaining budget is refused at arrival with `SAMD-SLM-8005` (HTTP 503) and a `Retry-After`

> while waiting is abandoned with `SAMD-SLM-8007` (HTTP 504) before generation starts.

The error registry gains one row, and the eight that precede it are unchanged and not
renumbered:

> | `SAMD-SLM-8009` | 422 | Prompt contains artifact control tokens |

### 15.8 Recorded, not acted on

**Dev connectivity from `backend/core` to this service.** An SSH local forward from the main
machine, which keeps the loopback bind on this box intact and encrypts the hop. Nothing about
the service changes for it. Production needs TLS or WireGuard, and that belongs on H-28's
residual list, not here.

**The infrastructure fixes deserve their own commit.** The drive moved to `/mnt/twotb`, the
system daemon's data-root relocated, and both compose HF-cache mounts repointed. Sections 9
through 13 are a record of being blocked by exactly these. The compose repointings are
carried in this commit because PR-5b had to correct both files anyway (one was an anonymous
volume, one was misindented, and the SLM one needed narrowing to the hub directory), but the
drive move and the data-root relocation are unrecorded in git and should be written up
separately.

### 15.10 State this session left the box in
